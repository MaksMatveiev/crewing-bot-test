# Крюинг-бот записи на интервью — дизайн

Дата: 2026-09-09
Статус: утверждён к реализации

## Что строим

Чат-бот крюингового агентства. Моряк заходит в веб-чат, выбирает открытую
вакансию (должность + тип судна), проходит скрининг по опыту и документам,
бронирует слот на интервью с крюинг-менеджером. Всё пишется в Postgres.

Рекрутер работает во второй вкладке того же приложения: заводит вакансии,
открывает слоты, читает заявки с вердиктами.

Это работа по заданию `rus md/PRACTICE.md`; за образец взят
`05-example_bot/bot.py` (барбершоп) — те же паттерны, своя ниша.

## Решения и их основания

| Решение | Почему так |
|---|---|
| Интерфейс — Gradio | Как в эталонном боте курса; готовый `render.yaml` для деплоя |
| Хранилище — только Postgres/Supabase | Бронь слотов требует транзакций; на Render файловая система стирается при рестарте |
| Диалог ведёт конечный автомат, не LLM | Модель `gemini-2.5-flash` на длинном диалоге путает порядок инструментов и выдумывает время; здесь на другом конце живой человек и реальный слот |
| Слот выбирается номером из списка, выданного базой | Выдумать несуществующий слот конструктивно невозможно |
| Скрининг даёт оценку, но не блокирует запись | Решение об отказе принимает человек, не модель |
| Вкладка рекрутера — пароль из `.env` | Адрес на Render публичный, а на вкладке контакты живых людей |
| Провайдер — Gemini | Единственный заполненный ключ в `.env` — `GOOGLE_API_KEY` |

## Данные

Четыре таблицы, создаются при старте через `CREATE TABLE IF NOT EXISTS`.

### `vacancies`
| Поле | Тип | Смысл |
|---|---|---|
| `id` | SERIAL PK | |
| `rank` | TEXT | Должность: Master, Chief Officer, 2nd Engineer, Bosun, AB, Cook… |
| `vessel_type` | TEXT | bulk carrier, tanker, container, reefer, general cargo… |
| `contract_months` | INT | Длительность контракта |
| `salary_usd` | INT | Ставка в месяц |
| `requirements` | TEXT | Текст требований — источник для RAG-ответов |
| `screening_questions` | JSONB | Список вопросов скрининга для этой вакансии |
| `is_active` | BOOLEAN | Показывать ли кандидатам |
| `created_at` | TIMESTAMPTZ | |

Вопросы скрининга живут в вакансии, а не в коде: для танкера спрашиваем
Tanker Endorsement, для балкера — нет.

Набор по умолчанию, который вкладка рекрутера подставляет в новую вакансию:
опыт в должности, типы судов, действующие STCW-сертификаты и срок годности,
паспорт моряка, визы (US C1/D, Шенген), английский (Marlins/CES),
медкомиссия, дата готовности к контракту.

### Бронь слота

```sql
UPDATE slots SET status='booked' WHERE id=%s AND status='open' RETURNING id
```

Ноль строк в ответе означает, что слот уже занят — бот обновляет список и
просит выбрать заново. Двойная бронь невозможна на уровне базы, а не на
уровне аккуратности модели.

### Одно активное интервью на моряка

Моряк не может записаться второй раз, пока не прошло уже назначенное
интервью. Активной считается заявка со статусом `new`, у которой слот ещё
в будущем.

Как только бот узнаёт контакт кандидата, он проверяет наличие активной
заявки. Нашлась — бот не ведёт человека по воронке дальше, а называет дату
и время, на которые тот уже записан, и предлагает обратиться к менеджеру,
если нужен перенос.

Если найденная заявка относится к слоту, который уже прошёл, бот сам
переводит её в статус `done` и спокойно записывает моряка заново. Ручной
работы рекрутера для этого не требуется.

Страховка в базе — частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS one_active_application
  ON applications (candidate_id) WHERE status = 'new'
```

Проверка в коде даёт человеку внятное объяснение, индекс не даёт гонке
двух вкладок создать две заявки на одного моряка.

## Модули

```
07-crewing_bot/
  funnel.py      конечный автомат воронки — без БД и без LLM
  db.py          вся SQL: схема, чтение, бронь, сохранение заявки
  brain.py       четыре вызова модели
  app.py         Gradio: вкладка кандидата + вкладка рекрутера
  knowledge.md   факты про агентство для RAG
  README.md      запуск и деплой
  tests/
    test_funnel.py
    test_db.py
```

Граница простая: `funnel.py` не знает ни про базу, ни про модель, поэтому
проверяется тестами целиком и мгновенно. `db.py` не знает про модель.
`app.py` только связывает три модуля с интерфейсом.

### `funnel.py`

Состояния: `GREETING` → `CHOOSING_VACANCY` → `COLLECTING_PROFILE` →
`SCREENING` → `CHOOSING_SLOT` → `CONFIRMED`.

Одна чистая функция перехода: текущее состояние + разобранные данные →
новое состояние + текст следующего вопроса. Никаких побочных эффектов.

### `brain.py`

| Функция | Паттерн курса | Задача |
|---|---|---|
| `classify()` | Router | Кандидат отвечает на вопрос воронки или задаёт свой? |
| `extract()` | Structured Output | Свободный текст → JSON с полями анкеты |
| `answer()` | RAG | Ответ по фактам агентства и текста вакансии |
| `verdict()` | Judge | Итоговая оценка кандидата с обоснованием |

Модель вызывается через ту же схему, что в `05-example_bot/bot.py`:
OpenAI-совместимый клиент, `base_url` Google, модель `gemini-2.5-flash`.

## Вкладка рекрутера

Открывается паролем `RECRUITER_PASSWORD`; до ввода пароля не показывает
ничего. Три блока:

1. **Вакансии** — список активных и форма добавления: должность, тип судна,
   длительность контракта, ставка, требования. Вопросы скрининга
   подставляются набором по умолчанию и правятся текстом.
2. **Слоты** — открыть слоты интервалом: дата, время начала и конца, шаг
   (по умолчанию 30 минут). Список открытых слотов с пометкой занятых.
3. **Заявки** — таблица: кандидат, вакансия, время интервью, опыт, дата
   готовности, вердикт модели. Свежие сверху.

Вкладка только читает и пишет через `db.py`; модель здесь не участвует.

## Поток разговора

1. Бот здоровается и показывает список активных вакансий из базы.
2. Кандидат выбирает вакансию.
3. Бот собирает анкету: ФИО, контакт, гражданство, опыт в должности,
   общий стаж, типы судов, дата готовности.
4. Бот задаёт вопросы скрининга из вакансии — по одному.
5. Бот показывает нумерованный список свободных слотов из базы.
6. Кандидат отвечает номером. Номер — индекс в списке, полученном из БД.
7. Бот бронирует слот и сохраняет кандидата и заявку — с пустым
   вердиктом. Только после этого зовёт `verdict()` и дописывает
   результат отдельным `UPDATE`. Порядок именно такой: отказ модели
   на последнем шаге не должен стоить кандидату брони.
8. Бот показывает подтверждение с датой и временем интервью.

На любом шаге Router ловит встречный вопрос («а какая зарплата?»): бот
отвечает по базе знаний и **повторяет текущий вопрос воронки** — состояние
не теряется.

## Отказы

| Ситуация | Поведение |
|---|---|
| Нет `DATABASE_URL` | Приложение стартует, чат честно сообщает, что база не подключена. Не падает |
| Модель не ответила | Извинение, состояние воронки не меняется, вопрос повторяется |
| Слот заняли, пока кандидат думал | `UPDATE` вернул ноль строк → список обновляется, просьба выбрать заново |
| Разбор ответа не удался дважды | Сырой текст уходит в `notes`, воронка идёт дальше |
| Моряк уже записан | Воронка останавливается, бот называет дату и время существующего интервью |
| Неверный пароль рекрутера | Данные не показываются, сообщение об ошибке |

## Тесты

Разработка по TDD: тест до кода.

- **`test_funnel.py`** — переходы состояний, встречный вопрос не сбивает
  воронку, выбор слота по номеру вне диапазона отклоняется. Без сети.
- **`test_db.py`** — против реальной базы из `DATABASE_URL`, пропускаются
  если переменной нет. Главный тест: две последовательные попытки брони
  одного слота — вторая обязана вернуть отказ. Второй по важности:
  моряк с активной заявкой не получает вторую, а тот же моряк с
  прошедшим интервью — получает.
- `brain.py` тестируется с подставной функцией вызова модели: проверяем
  разбор ответа, а не саму модель.

## Деплой на Render

К существующему `render.yaml` добавляется **второй** сервис — барбершоп
курса остаётся нетронутым и рабочим:

```yaml
  - type: web
    name: crewing-ai
    runtime: python
    plan: free
    buildCommand: pip install -r requirements.txt
    startCommand: python 07-crewing_bot/app.py
    envVars:
      - key: PYTHON_VERSION
        value: "3.12.6"
      - key: GOOGLE_API_KEY
        sync: false
      - key: DATABASE_URL
        sync: false
      - key: RECRUITER_PASSWORD
        sync: false
```

Порт берётся из переменной `PORT`, которую задаёт Render, с запасным
значением для локального запуска — как в `05-example_bot/bot.py`.

Известные особенности бесплатного плана:

| Что | Следствие |
|---|---|
| Сервис засыпает после ~15 минут простоя | Первый заход ждёт холодного старта. Для демо приемлемо, для живых кандидатов — нет |
| Render ходит по IPv4, прямое подключение Supabase — по IPv6 | Если строка `db.xxxxx.supabase.co:5432` не подключается, берём вариант **Session pooler** из того же окна Connection string. Проверяется на первом деплое |
| Файловая система стирается при рестарте | На нас не влияет: все данные в Supabase |

## Границы работы

Не входит в эту версию: письма и напоминания кандидату, отмена и перенос
брони, загрузка резюме файлом, многоязычность сверх зеркалирования языка
кандидата, интеграция с внешним календарём.
